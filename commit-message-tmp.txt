Fix registration-resume and volunteer-login reliability issues

- PaymentStep: persist "has the user clicked through to the ERP
  payment page" in the same localStorage progress object as the
  rest of the wizard, instead of local React state. Previously a
  reload after returning from payment (common on mobile - browsers
  frequently discard backgrounded tabs) correctly restored the step
  number but always re-showed the payment instructions screen
  instead of the transaction-ID entry form, reading as lost
  progress even though the registration itself was intact. Written
  synchronously to avoid a race with the same-tab navigation
  fallback below.
- PaymentStep: fall back to same-tab navigation when window.open()
  for the ERP payment link is blocked (common on mobile/in-app
  browsers e.g. WhatsApp/Instagram) instead of silently leaving the
  user on the transaction-ID form having never reached payment.
- Volunteer login moved from /vol/login to /vol-login, outside the
  volunteer PWA's service-worker cache scope (/vol/*), so it can
  never be served from a stale cached build on a volunteer's device
  (confirmed the current deployed bundle already points at the
  correct API domain - this specifically guards against devices
  still running an old cached build from before the Railway/API
  migration). Updated every redirect/navigate call site, the
  volunteer-invite email link generator, and the test. Kept a
  redirect at the old path for already-sent invite/reset emails.
